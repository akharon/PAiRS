# Configuration Reference

Quick guide to all configuration files in PAiRS.

---

## Configuration Files

| File | Purpose | Key Settings | Notes |
|------|---------|--------------|-------|
| `package.json` | Project dependencies | dependencies, devDependencies, scripts | npm workspaces |
| `tsconfig.json` | TypeScript compiler | target (ES2022), strict: true, module resolution | Strict mode enforced |
| `eslint.config.mjs` | Linting rules (flat config) | no-restricted-imports (blocks vscode in core) | Adapter boundary enforced |
| `package.json` | npm manifest + VS Code extension manifest | activationEvents, capabilities, contributes (the `languageModelTools` block is generated by `npm run sync-lm-tools`) | Extension entry point |
| `esbuild.mjs` | Bundler | minified in production; `--dev` / `--watch` unminified | Output: `dist/extension.js`, `dist/cli.js`, `dist/grammars/`, `dist/queries/` |
| `.vscodeignore` | `.vsix` contents | whitelist: the two bundles, grammars, queries, icon, README/CHANGELOG/LICENSE | Check with `npx vsce ls --no-dependencies` |
| `package-lock.json` | Locked dependencies | tracked; CI installs with `npm ci` | Regenerate with `npm install --package-lock-only` |
| `../.github/workflows/` | CI + release | `pairs-ci.yml` (typecheck, lint, test, build, package), `pairs-release.yml` (tag `pairs-v*`) | Repo root, not under `PAiRS/` |
| `.pairs/index.db` | SQLite code index | (auto-generated) | Safe to gitignore |
| `src/test/fixtures/*/` | Test projects | (mini codebases) | For integration tests |

## Critical Configuration Points

### Adapter Boundary Enforcement (G1 Rule)
- **`eslint` config**: `no-restricted-imports` blocks `vscode` outside `src/adapters/vscode/extension.ts`
- **Verified by**: `npm run lint` — fails if boundary violated
- **Why**: Keeps core editor-agnostic; CLI and extension share same logic

### TypeScript Strictness
- **`tsconfig.json`**: All strict flags enabled
- **Current**: Strict mode enforced; no implicit `any`, null checks, etc.
- **Violations**: Linter catches and fails build

### Tool Registration (Language Model Tools)
- **`src/adapters/vscode/package.json`**: Under `contributes.lm-tools`
- **Auto-discovery**: Extension reads `codeToolSchemas` and registers all tools
- **Format**: Each tool must have Zod schema in `src/core/tools/tools.ts`

### Code Store Facade
- **`src/store/graph/sqliteCodeStore.ts`**: Single entry point for all queries
- **No imports of low-level query functions**: Everything goes through facade
- **Reason**: Ensures consistency; single optimization point

### Extension / CLI Settings
- **`pairs.disabledTools`**: tool names not registered as Language Model Tools.
- **`pairs.skillLocation`** (`user` default | `workspace` | `off`): where the Claude Code skill is written. `user` = `~/.claude/skills/pairs/SKILL.md` (one copy for every project/worktree); `workspace` = `<folder>/.claude/skills/pairs/SKILL.md`. Only rewritten when content differs.
- **CLI**: global flags `--root <dir>` (or `PAIRS_ROOT`) and `--no-refresh`. Without them the root is the nearest ancestor of cwd holding `.pairs/index.db` or `.git`.
- **State dir**: `.pairs/` self-ignores via `.pairs/.gitignore` (`*`); PAiRS never edits the project's `.gitignore`. It also holds `index.lock` (cross-process full-index lock), `watcher.json` (heartbeat, refreshed every 30 s by the extension / `pairs watch`) and `last-refresh` (CLI auto-refresh throttle, 30 s).

### Sharing an index between Windows and WSL
- **Symptom**: `pairs` in WSL on a `/mnt/<drive>/...` checkout used to fail with `disk I/O error` while VS Code (Windows) had the same `.pairs/index.db` open. Cause: the index is a WAL database, and the `-shm` shared-memory file cannot be mapped by both OSes across the 9p/drvfs boundary (`SQLITE_IOERR`, errcode 4618). With no Windows holder, WAL on drvfs works.
- **Query commands** (code tools, `stats`, `query`, `files`) catch the I/O / cantopen / busy / locked class of open errors and reopen the index read-only: `file:<path>?immutable=1` (no locks, no `-shm`), else a temp-dir copy of `index.db` (+ `-wal`). They print one stderr line, skip auto-refresh, and never write or checkpoint. Content still in the `-wal` (not yet checkpointed by the extension) is missing from an immutable snapshot, so very recent edits may not show.
- **`index` / `watch`** cannot write across the boundary: they print one line and exit 1. Let the extension index, or use a WSL-native checkout (`--root <dir>`).
- **Same version on both sides**: a snapshot cannot be migrated, so if the extension and the CLI have different index schema versions, the CLI reports it in one line; reload/update the extension.

## How to Modify Common Configurations

### Add New Language Support
```typescript
// Edit src/core/indexer/parserRegistryImpl.ts

// 1. Register parser + query strings
const parsers: Record<Language, ParserConfig> = {
  golang: {
    parser: await wasmParsers.golang(),
    symbolQuery: '(function_declaration name: (identifier) @symbol)',
  },
  // ... Add new language
};
```

Then update tests:
```bash
npm test -- src/test/  # Verify parsing works
```

### Add New Tool
```typescript
// 1. Define schema in src/core/tools/tools.ts
export const newToolSchema = z.object({
  query: z.string(),
  options: z.object({ recursive: z.boolean() }),
});

// 2. Implement in src/core/tools/executors.ts
export async function executeNewTool(input: typeof newToolSchema) {
  // Query builder, return results
}

// 3. Register in codeToolSchemas
export const codeToolSchemas = {
  find_symbol: findSymbolSchema,
  new_tool: newToolSchema,  // Add here
};

// 4. Extension auto-discovers it as Language Model Tool
```

### Update TypeScript Target
```json
// Edit tsconfig.json under "compilerOptions"
{
  "target": "ES2022",    // Was ES2020
  "lib": ["ES2022", "DOM"]
}
```

### Disable a Linting Rule (Not Recommended)
```json
// Edit eslint.config.mjs (flat config), e.g. add a rules block:
{ files: ['src/**/*.ts'], rules: { 'no-restricted-imports': 'warn' } }  // Downgrade to warning
```

## Build & Package

**Development:**
```bash
npm run build       # Minified production bundles
npm run build:dev   # Unminified one-shot build
npm run build:watch # Watch mode (unminified)
```

**Testing:**
```bash
npm run test        # Run tests
npm run test:watch  # Watch mode
npm run check       # typecheck + lint + tests
```

**Packaging:**
```bash
npm run package        # Build .vsix (runs the production build via vscode:prepublish)
npm run install:vscode # Full pipeline: build → test → package → install
```
